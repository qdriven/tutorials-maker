# Ops Pipeline Template —— 一句话需求 → 领域模型开发 通用骨架

> 用法：复制本目录为新项目的 `ops/`；按文件顺序填写；每个文件头部标注【门禁】，未通过不得进入下一文件。
> 实例参考：本模板以「Slides 教学网站」需求为完整填充示例。

## 文件与阶段对应

| 顺序 | 文件 | 阶段 | 核心内容 | 门禁 |
|---|---|---|---|---|
| 0 | `constitution.md` | 框架宪法（项目级，一次编写） | 技术栈铁律、目录/命名/API/数据/测试规范、禁令、DoD | 新项目立项时评审一次 |
| 1 | `spec.md` | 需求分析 | 背景、角色、统一语言、**Schema 定义**、用户故事 + EARS 验收标准、边界情况、非目标、clarify 记录 | G1 需求评审（人工） |
| 2 | `design.md` | 方案设计 | **领域拆解**（限界上下文/聚合/领域事件）、**业务逻辑分拆到 User Story**（用例流程）、API 契约、前端状态设计、覆盖矩阵 | G2 设计评审（人工+自动） |
| 3 | `tasks.md` | 任务分解 | 任务卡（目标/文件/步骤/验证/依赖/执行者）、**依赖 DAG 与并行波次**、关键路径、覆盖率自检 | G3 计划评审（可自动） |
| 4 | `gates.md` | 全程 | 各阶段 Exit Criteria、**人工介入矩阵**（哪些必须人审/哪些可自动）、判定命令 | 每个门禁本身 |

## 填充原则
1. 每个字段都给了示例与填写说明；写不出的字段就是需求没说清，回到 clarify 环节追问，**禁止编造业务规则**。
2. 所有"术语"必须先入统一语言词汇表再使用。
3. 所有"任务"必须能回溯到至少一条用户故事；所有用户故事必须被至少一个任务覆盖（双向追溯）。
