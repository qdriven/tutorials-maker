# gates.md —— 阶段门禁与人工介入矩阵

> 全程适用。核心原则：**能写成命令的判定自动化；涉及意图与取舍的判定留给人。**
> 人工介入分三级：🔴 必须人审（阻塞式）｜🟡 默认人审，信任积累后可降级为自动+事后抽查｜🟢 全自动。

---

## 1. 阶段门禁总表

| 门禁 | 位置 | Exit Criteria（退出标准） | 自动判定方式 | 人工介入 |
|---|---|---|---|---|
| G0 | 宪法（项目级） | 宪法经团队评审；ADR 机制就位 | — | 🔴 架构负责人评审（仅项目立项/宪法变更时） |
| G1 | spec 完成后 | ① clarify 记录非空且无未决问题；② 每条用户故事有 EARS 验收标准；③ Schema 字段均有类型与约束；④ 非目标显式列出 | 规格 checklist 脚本（结构完整性可机器查） | 🔴 需求方确认"这就是我要的"（意图不可机器判定） |
| G2 | design 完成后 | ① 覆盖矩阵 100%；② 无违反宪法的设计（违禁技术/越界目录）；③ 每个上下文边界声明"不做什么" | `/analyze` 类交叉分析 + 宪法规则扫描 | 🟡 架构评审（标准项目可降级为抽查） |
| G3 | tasks 完成后 | ① 双向追溯 100%；② DAG 无环；③ 每任务有验证命令；④ 并行组内无文件冲突 | 全可机器判定 | 🟢 全自动（异常时升级人工） |
| G4 | 每个任务完成后 | 该任务的验证命令退出码为 0 | 沙箱执行 test/lint/build | 🟢 全自动；连续失败 3 次升级 🔴 人工 |
| G5 | 收敛（交付前） | ① 全部 EARS 对应验证通过；② 规约与代码一致（无 reconcile 残留）；③ 无宪法 §7 违反 | 测试套件 + 规约一致性 diff | 🔴 需求方验收（想法=实现，唯人工可判） |

## 2. 人工介入明细矩阵

| 介入点 | 为什么必须是人 | 输入给人的材料 | 人的动作 | 不介入的风险 |
|---|---|---|---|---|
| G1 需求评审 | "机器理解的=我想要的"只有需求方能判 | spec.md + clarify 问答表 | 批准 / 批注驳回 | 方向性返工（最贵） |
| G2 设计评审 | 上下文划分、聚合边界是长期架构取舍 | design.md + 覆盖矩阵 | 批准 / 调整边界 | 错误抽象长期累积 |
| G4 失败升级 | Agent 死循环/反复失败说明规约有洞 | 失败日志 + 任务卡 | 改规约或改任务，不是手改代码 | Token 空烧、错误叠加 |
| G5 终审验收 | 验收本质是业务判断 | 运行中的应用 + EARS 清单逐条演示 | 签收 / 打回（打回走收敛循环） | 交付"跑通但不对"的系统 |
| ADR 决策 | 宪法级变更影响所有未来需求 | ADR 草案 | 接受/拒绝 | 规范漂移 |

## 3. 可自动化的判定命令清单（示例项目）

```bash
# G2/G3 结构检查（示意）：spec 中每条 AC 是否出现在 tasks 覆盖表中
grep -o 'AC-[0-9a-z]*' ops/spec.md | sort -u > /tmp/acs.txt
grep -o 'AC-[0-9a-z]*' ops/tasks.md | sort -u | comm -23 /tmp/acs.txt -   # 输出应为空

# G4 任务验证（示例）
cd backend && mvn -q compile                                  # T1/T2
curl -sf http://localhost:8080/api/courses                    # T5
cd frontend && npm run build                                  # T6~T8

# G5 验收辅助
curl -sf -X POST http://localhost:8080/api/courses/1/qa \
  -H 'Content-Type: application/json' -d '{"question":"什么是阶段门禁"}'  # AC-03a
```

## 4. 信任演进路径

```
上线初期：  G1🔴 G2🔴 G3🟢 G4🟢 G5🔴        （三重人审）
稳定后：    G1🔴 G2🟡 G3🟢 G4🟢 G5🔴        （设计降级抽查）
成熟期：    G1🔴 G2🟢(抽查) G3🟢 G4🟢 G5🔴  （只留需求与验收两道人审）
```

> 经验法则：门禁降级的前提是该门禁连续 N 次（建议 ≥10）无人工修改通过；任何一次打回即恢复上级管控。
